- **Deploying with Docker:** Containers package an app with its Python runtime and dependencies for reproducible, isolated deployment; they are the most common way to deploy FastAPI. A container runs one main process (`CMD`) and lives as long as it does.
- **Project layout:** `app/__init__.py`, `app/main.py`, `Dockerfile`, and `requirements.txt`. The latter lists pinned dependencies installed with `pip`. With `uv add "fastapi[standard]" pydantic`, versions are locked in `uv.lock`; export and regenerate `requirements.txt` whenever `uv.lock` changes: `uv export --format requirements-txt --no-dev --no-emit-project --output-file requirements.txt`.
- **Dockerfile and cache:** Start from `python:3.14`, set `WORKDIR /code`, copy only `requirements.txt`, install with `RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt`, then copy `./app` to `/code/app`. Copying and installing dependencies before app code lets Docker reuse dependency layers when code changes. Start production with `CMD ["fastapi", "run", "app/main.py", "--port", "80"]`; `fastapi run` uses Uvicorn.
- **Exec-form CMD:** Use JSON exec form, not shell form (`CMD fastapi run app/main.py --port 80`). Shell form wraps the server in `/bin/sh`, which does not forward signals. Exec form lets FastAPI receive stop signals, shut down gracefully, and run lifespan shutdown; shell form can make `docker compose` take ~10 seconds to stop services.
- **TLS proxy:** If Nginx, Traefik, or a cloud load balancer handles HTTPS in front of the container, add `--proxy-headers` to trust `X-Forwarded-*` and generate correct `https://` URLs. See proxy documentation for forwarded headers and `root_path`.
- **Build and run:** `docker build -t myimage .`; `docker run -d --name mycontainer -p 80:80 myimage`; open `http://127.0.0.1/docs`.
- **Single-file apps:** For standalone `main.py`, copy it to `/code/` and use `CMD ["fastapi", "run", "main.py", "--port", "80"]`; `fastapi run` detects and imports it correctly.
- **Deployment concepts:** HTTPS and restarts are usually handled outside the app container by infrastructure/runtime. In a cluster, use one Uvicorn process per container and replicate containers; don’t add `--workers`. For a simple single-server app or single-machine Docker Compose where container replication is awkward, use multiple workers, e.g. `--workers`, `"4"`. One process per container gives predictable memory limits; with multiple workers, ensure processes × memory fits. Run migrations in a separate single container first when using many containers (e.g. Kubernetes *Init Container*); with one container, run them just before starting the app.
- **Old image and destinations:** `tiangolo/uvicorn-gunicorn-fastapi` is deprecated; `fastapi run --workers` / `uvicorn --workers` now manage workers. Deploy to Docker Compose, Kubernetes, Docker Swarm, Nomad, or a cloud container service.
