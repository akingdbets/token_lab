H1: DEPLOYMENT CONCEPTS, SERVERS AND workers
DEPLOY app = MAKE app AVAILABLE TO USERS; TYPICALLY ON REMOTE MACHINE,
RUNNING CONTINUOUSLY, EFFICIENTLY, RELIABLY.
OPTIONS: DEPLOY YOURSELF; USE CONTAINERS ([Docker](docker.md)); USE MANAGED
SERVICE, e.g. FASTAPI CLOUD ([HTTPS, TLS TERMINATION AND CLOUD PROVIDERS](HTTPS-and-cloud.md)).
SAME CONCEPTS APPLY, WHATEVER YOUR CHOICE.
H2: RUNNING THE SERVER: `fastapi run`
FASTAPI IS ASGI APPLICATION; ASGI SERVER RUNS IT.
`fastapi[standard]` INCLUDES UVICORN AND CLI:
```bash
fastapi run main.py
```
`fastapi run` STARTS PRODUCTION SERVER: LISTENS ON `0.0.0.0:8000`; AUTO-reload
OFF. VS `fastapi dev`, WHICH LISTENS ON `127.0.0.1` WITH reload ON.
FINDS `app` OBJECT IN MODULE, OR `[tool.fastapi] entrypoint` from `pyproject.toml`;
PRINTS USED import STRING, e.g. `main:app`.
UVICORN-DIRECT EQUIVALENT:
```bash
uvicorn main:app --host 0.0.0.0 --port 80
```
`main:app` MEANS "`app` OBJECT IN MODULE `main`", LIKE `from main import app`.
OTHER ASGI SERVERS INCLUDE HYPERCORN AND DAPHNE.
¬USE `--reload` IN PRODUCTION: USES MUCH MORE RESOURCES ∧ IS LESS STABLE;
DEVELOPMENT CONVENIENCE.
H2: MULTIPLE workers
ONE PYTHON PROCESS USES ONE CPU CORE FOR YOUR CODE.
SEVERAL CORES → run SEVERAL WORKER PROCESSES:
```bash
fastapi run --workers 4 main.py
# or
uvicorn main:app --host 0.0.0.0 --port 8080 --workers 4
```
MANAGER PROCESS LISTENS ON PORT ∧ DISTRIBUTES REQUESTS TO workers.
EACH WORKER IS SEPARATE PROCESS WITH ITS OWN MEMORY.
ML MODEL LOADED AT STARTUP LOADS ONCE PER WORKER; MEMORY USE MULTIPLIES.
ON KUBERNETES AND SIMILAR ORCHESTRATORS, USUALLY ¬USE workers;
run ONE UVICORN PROCESS PER CONTAINER; CLUSTER REPLICATES CONTAINERS.
H2: THE DEPLOYMENT CONCEPTS
SECURITY – HTTPS: WHO TERMINATES TLS ∧ RENEWS CERTIFICATES?
TOOLS: TRAEFIK, CADDY, NGINX + CERTBOT, HAProxy, KUBERNETES INGRESS,
CLOUD LOAD BALANCERS.
RUNNING ON STARTUP: WHAT STARTS SERVER WHEN MACHINE BOOTS, NOT YOU IN SSH SESSION?
TOOLS: DOCKER, KUBERNETES, DOCKER COMPOSE, SYSTEMD, SUPERVISOR, CLOUD SERVICE.
RESTARTS: WHAT RESTARTS PROCESS AFTER CRASH?
TOOLS: SAME TOOLS AS ABOVE.
REPLICATION: HOW MANY PROCESSES, ON HOW MANY MACHINES, BEHIND WHICH LOAD BALANCER?
TOOLS: `--workers`, KUBERNETES REPLICAS, MULTIPLE CONTAINERS.
MEMORY: HOW MUCH RAM DOES EACH PROCESS NEED × NUMBER OF PROCESSES?
TOOLS: MONITORING, `htop`.
PREVIOUS STEPS BEFORE STARTING: WHO RUNS DB MIGRATIONS ETC. ONCE, BEFORE
PROCESSES START?
TOOLS: KUBERNETES INIT CONTAINER, STARTUP SCRIPT.
NOTES:
SMALL ERRORS WITHIN REQUEST: FastAPI HANDLES; CLIENT GETS 500; PROCESS KEEPS SERVING.
WHOLE-PROCESS CRASH: EXTERNAL SUPERVISOR MUST RESTART PROCESS.
PREVIOUS STEPS (e.g., MIGRATIONS) run IN A SINGLE PROCESS, EVEN IF MANY workers
START AFTERWARD; OTHERWISE, PARALLEL MIGRATIONS CAN CONFLICT.
RESOURCE UTILIZATION: TARGET GOOD CPU/RAM USE (50–90%); IDLE SERVERS WASTE
MONEY; SATURATED SERVERS SWAP OR CRASH. MEASURE ∧ ADJUST.
LIFESPAN CODE ([LIFESPAN EVENTS](../app-structure/lifespan-events.md)) RUNS PER
PROCESS; IT IS NOT SUITABLE FOR ONE-TIME MIGRATIONS WITH MULTIPLE workers.

H2: PINNING FastAPI VERSIONS

FastAPI IS STILL `0.x`. UNDER SEMANTIC-VERSIONING CONVENTIONS FOR PRE-1.0 SOFTWARE:
- PATCH RELEASES (`0.112.1` → `0.112.2`): BUG FIXES ∧ NON-BREAKING CHANGES.
- MINOR RELEASES (`0.112` → `0.113`): MAY ADD FEATURES ∧ BREAKING CHANGES.
THEREFORE, PIN TO A MINOR RANGE OR EXACT VERSION:

```txt
fastapi[standard]>=0.112.0,<0.113.0
# or
fastapi[standard]==0.112.0
```

UPGRADE DELIBERATELY: HAVE TESTS ([TESTING WITH TestClient](../testing/testing-basics.md));
BUMP VERSION; run TESTS; FIX; THEN RE-PIN. CHECK RELEASE NOTES FOR CHANGES.
- DON'T PIN Starlette: EACH FastAPI VERSION REQUIRES ITS OWN COMPATIBLE Starlette RANGE.
- pydantic CAN BE PINNED TO ANY VERSION THAT WORKS WITHIN FastAPI'S SUPPORTED RANGE
  (THIS VERSION REQUIRES `pydantic>=2.9.0`).
