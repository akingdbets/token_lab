# 섹션 선택 압축기: 완료한 dev 평가와 해석

**단독 압축 결과에 대한 탐색적 dev 평가다.** 이번에 등록한 `section_bm25`로 35문항의 기존 70개 출력과 토큰·선택 목록이 일치했다. 조합 성능 실험은 포함하지 않는다.

## 35문항의 두 보존 범위

동일 질문·지시문으로 각 입력을 3회 독립 생성했다. BM25 순위를 고정하고 섹션 전체를 제외해 전체 입력의 80%·50% 이하를 목표로 했다. 최상위 코드 섹션 하나를 보존해 50% 목표를 조금 넘긴 문항은 4개다.

| 보존 목표 | 실제 입력 절감률 | 자동채점 평균 |
|---|---:|---:|
| 원본 전체 메시지의 80% | 22.45% | 98.25% |
| 원본 전체 메시지의 50% | 58.04% | 90.48% |

점수는 문항별 key_facts 충족 비율의 평균이다. 문항별 3회 평균은 29개 동일·5개 하락·1개 상승이었다. 이는 29문항이 모두 같은 이유로 맞혔다는 증거가 아니다. 원문·rule·LLMLingua-2를 같은 run에서 직접 비교하지 않았으므로 우위도 주장하지 않는다.

## 유형별 3문항의 중간 삭제 단계

fact·code·procedure·multi에서 각 3문항을 선정해 기존 두 입력 사이의 모든 중간 삭제 단계를 3회 평가했다. 추가 답변 201개와 기존 끝점 72개를 연결한 **91개 문서 상태·273개 관측**이다. 첫 오답 뒤에도 계속 평가했다.

문항은 과거 하락·유지 결과와 문서 다양성을 보고 선택했다. 같은 문서를 공유하는 문항도 있어 유형별 대표 표본이나 독립 문항 집합으로 해석하지 않는다. 끝점과 중간 단계의 호출 시점도 다르다.

- **9문항:** 관찰한 모든 상태·반복에서 자동 점수 만점. 더 줄인 구간이나 남은 정보의 기여는 확인하지 않았다.
- **c0029, DB fixture:** 1,217→1,163→916→815토큰에서 모두 만점. `Testing with a database`를 지운 443토큰에서 3회 모두 NOT FOUND.
- **c0039, JWT 로그인 실패:** 3,196→2,153토큰까지 모두 만점. JWT 예제 코드를 지운 1,237토큰에서 3회 모두 1/3점. 단순 로그인 400은 맞혔고 JWT 로그인 401·헤더는 답하지 못했다.
- **c0015, 토큰 비교:** 직접 설명을 지워도 아래 코드가 남아 있으면 username 사실을 3회 모두 충족했다. 코드 섹션도 제거한 뒤에는 3회 모두 해당 사실을 틀렸다.

```python
return {"access_token": user.username, "token_type": "bearer"}
```

| c0015의 상태 | 남은 근거 | username 사실 판정 |
|---|---|---|
| step_11, 2,196토큰 | 설명 + 코드 | 3/3 충족 |
| step_12, 2,132토큰 | 설명 제외, 코드 유지 | 3/3 충족 |
| step_13, 2,091토큰 | Related 추가 제외, 코드 유지 | 3/3 충족 |
| step_14, 1,694토큰 | 로그인 코드 섹션도 제외 | 0/3 충족 |

이 사례는 **직접 설명이 줄어도 코드에 같은 답이 남아 정답을 유지했을 가능성**을 뒷받침한다. 다만 섹션 전체 삭제이므로 특정 한 줄의 인과 기여·사전지식 배제를 입증하지 않는다. 선택적인 제거·복원과 무관 구간 대조가 후속으로 필요하다.

c0015의 총점은 중간에 오르내렸다. 두 번째 fact의 `create_access_token` 명시 기준에 판정 차이가 있어 첫 자동 비만점을 최초 근거 소실로 해석하면 안 된다. 위 fact별 검토는 원시 입력·답변을 대조한 분석이며 독립적인 사람 검수나 재채점이 아니다. 원래 자동 점수는 유지했다.
